# Saintdou Hotel OS v1.0｜核心一條龍現場驗收腳本

版本：第一階段・純前端離線版　｜　資料儲存：瀏覽器 `localStorage` 的 `SAINTDOU_HOTEL_OS_V1`

> 以下測試操作**會真的寫入本機資料**，請只在 DEMO／測試瀏覽器執行。正式上線前必須有 HTTPS、帳號權限、備份、證件資料保護及第二階段 GAS 後端。可先在 **W_CFG900** 匯出完整 JSON，再開始測試。

## A. 主要流程（建議 15 個檢查點）

| 順序 | 操作位置與步驟 | 預期驗收結果 |
|---|---|---|
| 1 | `W_PMS200` 點「新增房間」，建立 **901**，Standard，$80，VC | 房態矩陣顯示 901 / VC；新房間沒有 DEMO 標示 |
| 2 | `W_PMS210` 新增訂房：測試住客「Hotel E2E Guest」；房號 901；**入住昨天、退房今天**；Direct；房價 $80 | 訂房明細確認正確；如日期已有訂房，系統拒絕重疊 |
| 3 | 點訂房卡片 →「操作」→「辦理入住」 | 901 由 VC 轉為 OC；訂房狀態為 checkedIn |
| 4 | `W_FNB400` 在 POS 選「Espresso」×2；付款選 **ROOM**、指定 901；確認 | 建立 POS 餐單；房帳新增 **$7** 的 F&B 應收；Coffee Beans 的廚房庫存扣 **0.04 kg** |
| 5 | `W_FNB410` 查看 KDS，依序「開始製作」→「完成備餐」→「送達」 | 狀態依 new → preparing → ready → served；不得倒退已送達工單 |
| 6 | `W_HKE300` 使用 MiniBar：在住房 901、Water ×1、售價 $2.50 | FLOOR 備品扣 1 瓶；901 房帳新增 **$2.50** MiniBar 應收 |
| 7 | `W_PMS220` 打開測試住客的 Guest Folio | 退房前可見 F&B $7 + MiniBar $2.50；過去尚未過帳的房費在退房操作補記 |
| 8 | 按「退房結帳」；付款 Cash，應付 **$89.50**，實收 **$100.00** | 找零 **$10.50**；訂單 checkedOut；現金收款只記 $89.50，不把找零算收入 |
| 9 | 返回房態矩陣 | 房間 901 自動轉為 **VD**（空髒）；不可在未清潔狀態直接入住 |
| 10 | `W_HKE300` 找 901 的 checkout 清潔工單（high priority）→開始清潔 | 生成獨立 HK 工單，狀態為 cleaning |
| 11 | 房務點「送交查房」，主管點「查房通過」，可勾領用 Soap ×1 | 狀態 inspection → done；901 轉為 **VC**；若領用備品，FLOOR 庫存減 1 |
| 12 | `W_PMS230` 日期設「今天」，點夜審；輸入與系統 Cash expected 相符的實點現金 | 夜審建立不可重覆的當日日結快照；本期 OCC / ADR / RevPAR 由過帳資料重算 |
| 13 | 對同一天再次按夜審 | 系統拒絕重覆過帳，歷史日結仍保留 |
| 14 | `W_FIN700` 檢查 USALI 風格 P&L | 客房、F&B、其他收入分開；房費／餐飲不會因收押金、退款或 AR 再次認列；GOP 由收入減部門成本與營運費得出 |
| 15 | `W_CFG900` 匯出 JSON，開新分頁／重新整理，再匯入備份 | 房間、住客、房帳、工單、庫存、照片及稽核事件可恢復，資料不會重覆產生 |

**關於第 8 步房費**：DEMO 已經夜審到昨天。若今天才補登一張「昨天入住、今天退房」的新訂房，系統會把 $80 房費以「已結日期調整分錄」記在**今天**，而不改寫昨天已關帳的日結快照。房帳仍會正確結為 $89.50。上述金額以沒有其他測試交易、價格沒有被更改為前提。

## B. 拒絕錯誤操作（負向測試）

| 測試 | 預期結果 |
|---|---|
| 同一房間、相同日期再建一筆訂房 | 阻擋重疊，不新增訂房 |
| `W_SCM500` 扣庫數量大於現有 MAIN / FLOOR / KITCHEN 數量 | 阻擋負庫存，流水帳不新增 |
| 在退房房帳嘗試修改歷史已過帳金額 | 只能新增**沖銷**，不改原始單據 |
| 在 Guest Folio 退款金額大於原收款剩餘可退金額 | 拒絕超額退款 |
| 已送達 KDS 訂單回退「開始製作」 | 拒絕狀態倒退 |
| 重複夜審同一天 | 拒絕重複過帳 |
| `W_SCM510` PO 100 件已收 40 件，再驗收 61 件 | 拒絕超量，保持 40 件已收 |
| 無供應商發票號碼時核對 AP | 拒絕三方核對 |
| 有正式 POS 訂單引用 DEMO 食材／菜單，卻按清除所有 DEMO | 阻擋清除，保護正式交易關聯 |
| GAS URL 留白時按雲端上傳 | 明確顯示尚未設定 URL；不假裝成功，離線操作仍正常 |

## C. 其他操作功能

- **卡片／表格切換**：房間、訂房、餐飲菜單及餐單、原料庫存、固定資產、員工、報修等列表。
- **PSJHR 式詳情**：卡片點入詳細頁，頂部切基本資料／帳務異動／關聯單據／操作；內頁上下滑動續看下一筆，上方分頁可水平滑動切換。
- **背景自訂**：右上 🎨 → 8 種色票、背景圖、遮罩透明度。
- **照片**：詳細頁 📷 → 相機或手機相簿，Canvas 自動縮圖並加文字標示。照片進 JSON 備份；本機配額不足時不會虛報成功。
- **CSV**：安全主檔可直接匯入新增；訂房、金流等有風險的 CSV 暫存至待覆核區，不直接改動正式帳務。
- **日／週／月／年**：切換 KPI 及期間流水，確認已過帳的費用及收入按選定範圍重算。
- **Cloud event queue**：所有變更產生 `{eventId,type,at,propertyId,actor,payload}`。Phase 1 可離線累積事件；真正的遠端 API 需 Phase 2 提供 `Code.gs` 後才可驗證。

## D. 已執行的自動化模型測試

本次開發使用 JavaScript VM 針對純資料邏輯進行核心流程測試，成功驗證：20 間 DEMO 客房初始化、三個月示範訂房與夜審、訂房→入住→POS 房帳→退房現金找零→房務查房→夜審、禁止重覆夜審、禁止負庫存、採購驗收→AP 核對與付款、DEMO 引用保護、退款上限、餐單作廢的反向沖銷、已關帳日期的房費調整及 CSV 特殊字元解析。全部 15 個模組的 HTML 渲染函式也經過程式層級呼叫檢查。

**範圍限制**：上述是 JavaScript 邏輯／靜態渲染檢查，不等於已在所有 Android／iOS／桌面瀏覽器完成手指滑動及相機實機驗收。第一階段沒有接入使用者的實際 Telegram、Google Sheets 或 GAS；其後端、權限驗證、資料同步及真實交易環境仍待第二階段。
